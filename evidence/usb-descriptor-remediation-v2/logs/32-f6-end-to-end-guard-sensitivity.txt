# F-6 closure: the end-to-end guard, and the sensitivity measurement that justifies it
# captured 2026-11-21T20:06:43Z

Finding F-6 asked for "one end-to-end test that dies if the `_relations` UNKNOWN path is
weakened". `tests/test_pc5ctl_usb_topology_unknown.py` is those tests. Two things had to be
measured before writing them, and both overturn the mechanism the finding (and this
package's earlier draft) named.

## 1. Why `test_20`/`test_21` cannot localise the decision at all

Both chmod `devices/sda/slaves` / `devices/sda/holders` and assert a CLI refusal. Under `m7`
they still pass — but not because a *second* guard fires instead. `root_closure()` walks the
root disk and interrogates each child directory it lists, so an unreadable child of `sda`
makes `partitions_of()` answer UNKNOWN as well. The refusal is overdetermined by the fixture,
which means neither test can ever distinguish "the relationship reader is right" from
"something else in the walk noticed". Instrumented, mutant active, refusal still present:

## 2. The fixture that does isolate it

Move the unreadable directory one level down, to a device the *only* reader of which is the
`_relations` call the walk performs for the root partition:

| fixture directory chmod 000 | `_relations` answer | `root_closure()` | rc | `dd` calls |
|---|---|---|---|---|
| `devices/sda/sda1/holders` — real code | `UNKNOWN` | `UNKNOWN` | 1 | 0 |
| `devices/sda/sda1/holders` — under `m7` | `[]` | `{(8, 0), (8, 1)}` | **0** | **1** |
| `devices/sda/sda1/slaves` — real code | `UNKNOWN` | `UNKNOWN` | 1 | 0 |
| `devices/sda/sda1/slaves` — under `m7` | `[]` | `{(8, 0), (8, 1)}` | **0** | **1** |
| `devices/sdc/holders` (below the target) | `UNKNOWN` | `{(8, 0), (8, 1)}` | 0 | 1 — both ways |
| nothing unreadable (control) | `[]`/`[]` | `{(8, 0), (8, 1)}` | 0 | 1 |

The target-side row is the boundary the last case records: the closure is rooted at the
device backing `/`, so an unreadable relationship *below* the target is not this guard's
business; a device the root depends on is always reached through the root's own
`slaves`/`holders`, which the two refusing rows pin.

The control and the target-side boundary case keep passing under the mutant, which is the
point: they are not the guards. The two that fail are, and the message each prints names the
property it is protecting before it reports the mutant's answer.

`INTENTIONS["m7-unreadable-topology-is-empty"]` in that harness now lists the two new names
beside `test_unreadable_slaves_is_unknown_not_empty`, and the harness asserts each is present
in the loader's inventory and fails under the mutant — so this closure cannot rot silently the
way the v1 mapping did (finding F-5).

F-6 is therefore **closed by a test that dies**, which is what §10.3 of the review asked for,
and `FINDINGS-DISPOSITION-20261121.md` records the corrected mechanism next to the
superseded guess rather than replacing it.
