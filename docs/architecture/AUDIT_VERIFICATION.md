# Verification of the 2026-11-16 audit's findings

The audit that prompted this phase is **not in this repository**: no
`docs/architecture/MISSION_AUDIT_2026-11-16.md` exists on `main` or on this
branch, and no branch named `audit/mission-alignment-2026-11-16` exists either.
Its findings therefore could not be read from a file; each claim was re-derived
from the tree, and this table records what the tree actually says.

Verdicts: **VERIFIED** (the claim matches the code), **PARTIALLY VERIFIED**,
**NOT VERIFIED** (could not be reproduced), **OUTDATED** (was true, no longer is),
**DISPUTED** (conflicting measurements), **REQUIRES OWNER ACTION**.

| # | Finding as stated | Verdict | Evidence |
|---|---|---|---|
| 1 | The UEFI loader does not bring up a 64-bit kernel; it drops to 32-bit protected mode | **VERIFIED** | `boot/uefi/bootx64.S`: a far return into a 32-bit compatibility segment, then `CR0.PG` cleared, then `ljmp $CODE32_SEL, $KERNEL_ADDR`; `boot/uefi/uefi_main.c` documents the 32-bit contract and pins `sizeof(struct pc5_boot_info) == 104` |
| 2 | There is no long-mode entry path and no PC5-owned paging | **VERIFIED before this phase, OUTDATED now** | the path did not exist; it exists since this branch (`boot/uefi64/`, `kernel64/`, `docs/ARCHITECTURE.md` §7) and is implemented, unit-tested and stub-firmware-tested, not firmware-tested |
| 3 | A `-m32` → `-m64` flag flip was presented as a 64-bit kernel | **NOT VERIFIED** | no such change exists on `main`; the flag set for the 32-bit kernel is unchanged, and the new path uses its own `-m64 -mno-red-zone -mcmodel=small` build with its own linker script |
| 4 | The roadmap's `M2` / `M2a` / `M2b` dependency order is wrong | **VERIFIED** | `M2` (PCIe, MSI/MSI-X, NVMe) depended only on `M0`/`M1` while `M2a` (long mode, APIC, SMP, timers) depended on `M2`. Corrected to `M2a → M2`, `M2b` after both; `tests/test_roadmap_dependencies.py` fails if it regresses |
| 5 | Two versions (`0.2.0`, `0.4.0-dev`) are published without saying which is the product's | **VERIFIED** | `Makefile VERSION ?= 0.2.0` and `roadmap.json "version": "0.4.0-dev"`. Now: `Makefile VERSION` is the single product-version source, the roadmap carries `document_version`, and the README shows both, labelled |
| 6 | The LFS object for `PS5UPDATE.PUP` returns 403, contradicting the documentation | **DISPUTED** | a read-only batch-API query on 2026-11-16 returned HTTP 200 with a `download` action for oid `42ea0e5a…b063fb` and size 1,423,697,408, matching the 135-byte pointer; no payload was fetched. The document now records the measurement and its date |
| 7 | The audit itself is committed under `docs/architecture/MISSION_AUDIT_2026-11-16.md` | **NOT VERIFIED** | the file does not exist; nothing was overwritten, and this table is the record instead |
| 8 | `psm/` presents platform-model conformance as working PS5 behaviour | **PARTIALLY VERIFIED** | `psm/` is a contract plus conformance doubles; `M10` remains `in_progress`, and `docs/PS5_COMPATIBILITY_STATUS.md` states no PS5 software has been executed. The code and the documents agree; the risk is in a reader's expectations, not in a claim |
| 9 | Milestone states overstate progress | **PARTIALLY VERIFIED** | `M2`, `M2a`, `M2b`, `M3` are all `not_started`, and the long-mode work is recorded as foundation `F64`/`F64M` with explicit "does not complete" lists rather than as milestone progress |
| 10 | Version/progress figures in the README are hand-written | **NOT VERIFIED** | the README's statistics block is generated by `tools/presentation.py` and `make presentation-check` fails on any hand edit |

## What this table is not

It is not a verdict on the audit's other claims: an audit that is not in the tree
cannot be quoted, and a claim that was not re-derived here is not repeated. Where
the audit and the tree disagreed, the tree and a dated measurement win, and the
disagreement is left visible rather than smoothed over.
