# M0–M8 dependency graph

The milestone graph is **data**, not prose: `docs/architecture/roadmap.json`.
`tools/roadmap.py` validates it, renders the block below from it, and
`tests/test_architecture.py` runs both in `make check`. The graph therefore
cannot drift from the document without failing a test.

Why the graph is the right place to encode the architecture: the directive's
central promise is *"Track B must never block Track A."* A dependency edge is
the only place that promise can be broken accidentally, and it is the only place
a machine can check it.

## 2. How to read it

| Field | Meaning |
|---|---|
| `id` | stable milestone id, `M<number>` with an optional letter for sub-milestones that already exist in this repository |
| `track` | `A` = PC5 Native (installable operating system), `B` = Prospero (research and compatibility) |
| `state` | `complete`, `in_progress`, `blocked`, `not_started` — nothing else is accepted |
| `depends_on` | milestone ids that must reach their acceptance criteria first |
| `deliverables` | artefacts that must exist in the tree |
| `acceptance` | measurable conditions; "documented" is never one of them |
| `evidence` | repository paths a reader can open; required when `state` is `complete` |
| `blocker` | required when `state` is `blocked`, and it must name an owner-actionable condition |
| `legacy` | where the milestone came from in `docs/ROADMAP.md`, so no history is lost |
| `next_action` | the single next thing to do; present on every milestone a session may pick up |

## 3. The enforced Track A / Track B gate

`validate()` computes the transitive dependency closure of every Track A
milestone and fails if any Track B milestone appears in it:

```
track gate violated: Track A milestone M3 depends on Track B milestone M5
```

This is a rule about the *release path*, not about cooperation. Track B may
consume anything Track A produces — that is the point of shared platform
services — and Track B may be the reason a future Track A feature exists. What
it may never do is sit between a Track A milestone and its delivery. If Prospero
research stops tomorrow, M1 through M4 and M7 through M8 must still be
achievable; the graph is the proof that they are.

Two Track B milestones exist and both depend only on M0:

* **M5 — PS5 executable compatibility.** The only Track B work that can produce
  a runnable result with lawful inputs today (relinking + independently
  implemented PRX shims). It is *not* firmware execution and its acceptance
  criteria forbid saying so.
* **M6 — Genuine Prospero research.** Feasibility, boot-chain dependency
  mapping and a legal assessment. It is gated on counsel-grade review before any
  experiment, and its deliverable is a go/no-go recommendation — not a promise.

## 4. Critical path

The critical path is the longest Track A chain:

```
M0 -> M1a -> M1 -> M2 -> M3 -> M4 -> M7 -> M8
```

Reading it as engineering: the architecture work (M0) is done; the reproducible
medium (M1a) is done; everything else on the path is ahead. The two highest
leverage edges are:

1. **M1c → M1.** The UEFI loader is implemented and executed against a stub, but
   a physical UEFI machine cannot be claimed until it boots under real firmware.
   This is the cheapest edge to close and it unblocks the installer.
2. **M1 → M2.** Storage *write* support is the single missing capability that
   blocks installation, a writable filesystem, updates, recovery and every
   hardware test that needs to persist a log.

M1b (CI publication) hangs off M1a and only joins the critical path at M8, which
is why its blocked state does not hold up engineering work.

## 5. M0–M8 against the repository's existing milestones

The directive renumbers the milestones. Nothing already proven is discarded; the
existing records in `docs/ROADMAP.md` and `docs/TEST_RESULTS.md` stay as the
historical evidence, and this table maps them.

| Directive milestone | Repository milestone(s) | State today |
|---|---|---|
| M0 architecture freeze and audit | repository M0 | COMPLETE — this deliverable set extends it |
| M1 physical boot and installation | repository M2 (physical), M3 (installer part) | NOT STARTED; prerequisites M1a and M1c carry the proven work |
| M2 hardware abstraction and drivers | repository M3 (services), M6 (input/network) | PARTIAL: firmware-level inventory only, no driver for any device class that needs one |
| M3 PC5 operating system | repository M3 | NOT STARTED |
| M4 PlayStation experience | repository M3/M6 (interface) | NOT STARTED |
| M5 PS5 executable compatibility | repository M7 (execution path) | RESEARCH; nothing executed |
| M6 genuine Prospero research | repository M4, M5 | BLOCKED on both a lawful path and legal review |
| M7 performance and compatibility expansion | repository M8 | NOT STARTED |
| M8 release-quality PC5 | repository M9 | NOT STARTED |
| (kept as sub-milestones) | repository M1, M1b, M1c | M1a complete; M1b blocked; M1c in progress |

Sub-milestones are kept rather than folded into M1 because they have their own
evidence and their own partial states. Flattening them would either overstate
progress (calling M1 "in progress" when no disk has ever been written) or lose
the record of what was proven.

## 6. Gates

A gate is a point where proceeding without evidence would corrupt every
subsequent claim. The graph marks them by acceptance criteria; this is the short
list an agent must respect:

| Gate | Between | Rule |
|---|---|---|
| G1 | M1a/M1c → M1 | no installation claim until a physical machine boots and the log is committed |
| G2 | M1 → M2 | no "driver supported" claim until a measured compatibility row exists for that device |
| G3 | M2 → M3 | no shell work on hardware that cannot yet display, store and take input reliably |
| G4 | M3 → M4 | no PlayStation-experience claim before the base OS installs and boots unattended |
| G5 | M0 → M5/M6 | no Prospero experiment without the legal assessment and the isolation rule |
| G6 | M7 → M8 | no release before every qualified machine has release-build evidence |

## 7. Keeping the graph honest

* Change a milestone by editing `roadmap.json`, then run
  `python3 tools/roadmap.py sync` and commit both files.
* `make check` fails if the JSON is invalid, if a Track A milestone depends on a
  Track B milestone, if a complete milestone has no evidence, if an evidence
  path is missing, or if this document's generated block is stale.
* A milestone state may only move forward with a link in `evidence`. Moving a
  state backwards is allowed and encouraged when a claim is found to be
  unsupported — the audit in this directory did exactly that to several
  documents.
