## 2. Confirmed defects

### D1 — CRITICAL: the "4 GiB identity map" is a 1 GiB map (PR #26, still present in PR #27)

`boot/uefi64/pagetables.c:34-35`

```c
store(pc5_pt_pml4(pt), pc5_pt_pdpt(pt) | 1ull | 2ull);   /* present, writable */
store(pc5_pt_pdpt(pt), pc5_pt_pd_base(pt) | 1ull | 2ull);   /* only PDPT[0] */
```

All four page-directory pages are allocated and all 2048 leaf entries are written, but
**only the first PDPT entry is installed**. One PDPT entry maps exactly one 1 GiB PD, so
only `0x00000000–0x3FFFFFFF` is reachable. PDPT[1..3] are left holding whatever the
firmware left in that memory (they are never zeroed either — `pc5_pt_build_identity`
clears the PDPT at offset `+4096` but not entries `+8..+31` of it).

The function returns 2048 and the loader's own success test
(`uefi64_main.c:550`: `mapped != PC5_PT_SPAN / PC5_PT_2MIB`) passes, so nothing
notices.

Verified against the real `pagetables.c` compiled on the host, block poisoned with `0xAA`:

```
pc5_pt_build_identity returned 2048 (expected 2048)
loader check 'mapped == span/2MiB' -> PASS (proceeds)

0x00000000  MAPPED     0x83
0x3FFFFFFF  MAPPED     0x3fe00083
0x40000000  unmapped   0x0      <-- first byte above 1 GiB
0x80000000  unmapped   0x0
0xC0000000  unmapped   0x0
0xFFFFFFFF  unmapped   0x0

PDPT[0] = 0x000055fdab36d003 (present)
PDPT[1] = 0xaaaaaaaaaaaaaaaa (NOT PRESENT)
PDPT[2] = 0xaaaaaaaaaaaaaaaa (NOT PRESENT)
PDPT[3] = 0xaaaaaaaaaaaaaaaa (NOT PRESENT)
```

**Consequences, all of which the code claims to have handled:**

1. `pc5_pt_mark_uncached()` reports 4 entries changed for a framebuffer at 2 GiB and
   writes them into PD pages that no PDPT entry references — the interface is *lost*
   and the UC bits are set on unreachable memory. Reproduced:
   `pc5_pt_mark_uncached(2GiB..2GiB+8MiB) changed 4 entries` / `lookup(2GiB) mapped=0`.
2. A framebuffer anywhere in `[1 GiB, 4 GiB)` passes every check the kernel performs
   (`pc5_range_within` against `identity_span`, then `pc5_map_covers`) and is reported
   `usability=ok`, while the MMU has no mapping for it:

   ```
   FB at 64 MiB    within-span PASS  actual mapping MAPPED
   FB at 1 GiB     within-span PASS  actual mapping UNMAPPED  <-- kernel would fault on first write
   FB at 2 GiB     within-span PASS  actual mapping UNMAPPED
   FB at 4032 MiB  within-span PASS  actual mapping UNMAPPED
   ```

   This is latent, not immediate: `kernel64` never dereferences `framebuffer_addr`
   (it only prints usability), so today it produces a **false statement** rather than a
   crash. It becomes a hard fault the moment anything paints the screen, which is the
   stated purpose of the map.

**Why every gate is green:** a correct 4 GiB implementation passes all 40 tests
unchanged. In `/tmp`, with no test file edited, replacing the single PDPT write with a
per-1 GiB loop yields:

```
Ran 40 tests in 4.038s
OK
```

and with the fix the lookups become `0x40000000 → MAPPED`, `0x80000000 → MAPPED`,
`0xC0000000 → MAPPED`, `0xFFFFFFFF → MAPPED`. **The test suite cannot distinguish a
1 GiB map from a 4 GiB map**, because `test_pagetables64.py` asserts PD entries
directly (`self.block.entry(1024)`, `.entry(2047)`) and only ever calls `pc5_pt_lookup`
at `0x100000` and at `SPAN`. Specifically:

- `test_pagetables64.py:150` — `assertEqual(pc5_pt_lookup(base, SPAN, …), 0)` passes
  *because* the map is broken (it also passes when correct, since `SPAN` is exclusive).
- `test_boot64_stub.py:167-172` — `test_a_framebuffer_ending_exactly_at_the_span_is_accepted`
  asserts `framebuffer=0xffd00000` with no `unusable=` marker. `0xFFD00000` is inside
  the unmapped hole. **The test enshrines the defect as the expected behaviour.**

This is also a documented false negative: `docs/TEST_RESULTS.md:2764-2765` records the
concern as **"disproven"** with the arithmetic `(pages − 2) × 512 × 2 MiB = 4 GiB`.
That computation counts PD pages and never accounts for the fact that a PDPT entry is
consumed by the PD *pointer*, so four PD pages require four PDPT entries. The review
that produced that row asked the right question and answered it wrongly.

`docs/ARCHITECTURE.md:266` nonetheless states "an identity map below 4 GiB", and
`docs/TEST_RESULTS.md:2667` repeats "identity map below 4 GiB". Both are false as
shipped.

### D2 — CRITICAL: `alloc_below_4g()` requests nothing (PR #26, still present in PR #27)

`boot/uefi64/uefi64_main.c:233-243`

```c
u64 address = 0;
efi_status status = g_bs->allocate_pages(EFI_ALLOCATE_MAX_ADDRESS,
                                        EFI_LOADER_DATA, pages, &address);
```

UEFI 2.9A §7.2.1: *"Allocation requests of Type AllocateMaxAddress allocate any
available range of pages whose uppermost address is less than or equal to the address
pointed to by Memory on input."* `address` is on **input** as well as output, and it is
initialised to `0`. A range of one or more pages cannot have its uppermost address
≤ 0.

Confirmed in the reference implementation (edk2 `MdeModulePkg/Core/Dxe/Mem/Page.c`,
`CoreInternalAllocatePages`): `Start = *Memory;` … `if (Type == AllocateMaxAddress) {
MaxAddress = Start; }` … `FindFreePages(MaxAddress, …)`, which then searches only below
`0`. The parameter is also `IN OUT EFI_PHYSICAL_ADDRESS *Memory`.

The intent is clear from the header comment ("requests every allocation below the
region") and the guard two lines below (`address > LOAD_LIMIT`). The correct call is
`address = LOAD_LIMIT;` before the call. Note the sibling call at `uefi64_main.c:321`
uses `EFI_ALLOCATE_ADDRESS` correctly, which makes the omission look like an oversight
rather than a misunderstanding.

**Reproduced end-to-end.** I copied the harness to `/tmp` and patched *only* the stub's
`svc_allocate_pages` so that `EFI_ALLOCATE_MAX_ADDRESS` honours its input as the spec
requires (return `EFI_INVALID_PARAMETER` for `0`). Then I ran the **unmodified, repo-built**
`build/uefi64/BOOTX64.EFI` and `build/kernel64/KERNEL64.BIN`:

```
=== unmodified repo stub ===
PC5-64-LOADER-BANNER 64-bit UEFI path (experimental)
…
PC5-64-LOADER-JUMP entry=0x100000 …
PC5-64BIT-LONG-MODE-OK          <-- whole path passes

=== same binaries, spec-conforming AllocateMaxAddress ===
PC5-64-LOADER-BANNER 64-bit UEFI path (experimental)
PC5-64-LOADER-FAIL=bootinfo-allocate     <-- dies at the first allocation
```

So `make stubtest64` 22/22 and the `PC5-64BIT-LONG-MODE-OK` marker are green **only**
because the stub does not implement the API it is standing in for.

**Why every gate is green:** `tests/uefi_stub_firmware.py:700` ignores `alloc_type`
entirely —

```python
def svc_allocate_pages(self, alloc_type, memory_type, pages, memory_ptr, *_):
    self.write_u64(memory_ptr, self.alloc(pages * 4096, align=4096))
```

The stub contains no `EFI_ALLOCATE_*` constant at all, and always allocates from a
fixed low pool ending at `0x03000000`. Every address it returns happens to satisfy
`address > LOAD_LIMIT`-style checks, so the contract is never exercised. Worse,
`tests/boot64_stub.py:82-83` documents the high-allocation window as ending *"exactly
at the top of PC5's identity span"*, and
`test_handoff_regions_placed_just_below_the_span_limit` depends on that claim. It does
not: `HIGH_WINDOW = (0x0FF00000, 0x00100000)` ends at **`0x10000000` = 256 MiB**, which
is **16× short** of the 4 GiB span. The test named "just below the span limit" never
approaches the limit, so it could not have caught either D1 or D2 — and the comment
that justifies it is arithmetically false.

## 3. Risks

- **R1 — the loader↔kernel contract is only as good as the stub.** D1 and D2 both
  survived a full review, a green 654-test suite, 22/22 stub checks and a written audit
  because the stub is more permissive than firmware. Anything the loader does *through*
  a boot service is unverified until the stub models that service faithfully.
  Highest-value follow-up: make the stub enforce `AllocateMaxAddress`, and add a test
  that walks the map at `1 GiB`, `2 GiB` and `4 GiB − 2 MiB` via `pc5_pt_lookup`.
- **R2 — `ovmf-test` has never run.** All 22 firmware-matrix rows are unexecuted
  (`not-tested`, exit 2). D2 would very likely have been caught on the first real
  firmware boot. The risk is not that the gate is missing — it is well built and CI
  fails on exit 3 by design — but that a *long* green record exists over a path real
  firmware has never touched.
- **R3 — `PC5_PT_PAGES`/span assumptions are load-bearing and untested end-to-end.**
  The kernel recomputes `identity_span` agreement, which is good, but nothing validates
  that the installed tables actually realise the span they declare.
- **R4 — no physical hardware, no Sony execution.** Correctly and repeatedly stated
  everywhere I checked; not a risk of overclaiming, only of the record being read as
  more than it is.

## 5. Phase 2 — the rest of PR #26

Reviewed in full, not only the 64-bit path.

**Genuinely good, and verified rather than taken on trust:**

- `bootx64.S` failure path restores **CR3 before** `popfq` unmasks interrupts — correct
  ordering, and the comment explains why.
- Handoff is assembly so that "nothing runs on the new map" is a property of the
  instruction sequence; `RSP` is only moved after CR3 is read back and compared.
- `_Static_assert`s pin `stack_top` at offset 88 and the ABI at 160 bytes from both
  sides, so a layout change breaks the build rather than the jump.

  validating it (`start.S` → `pc5_adopt_stack`), which fixes a real
  untrusted-`RSP` fault.

  check (`kernel64/main.c:456`).
- `conventional_pages` accumulation cannot overflow: `pc5_descriptor_valid` bounds
  `page_count` to `2^52−1` and validation precedes accumulation, so 1024 entries cap the
  sum near `2^62`. I initially suspected this and proved it is safe.
- 32-bit release path is untouched: `$(ISO)` depends only on `loader.bin`, `mbr.bin`,
  `kernel.bin`, `efi.img`, `ISO/README.TXT`, `ISO/BUILDINFO.TXT`, `tools/mkiso.py`.

## 8. Phase 6 — release isolation

**Stronger than claimed, after controlling for the one thing that makes naive
comparisons meaningless.**

First finding: the ISO is **not** bit-reproducible by default, because
`STAMP_EPOCH ?= $(or $(SOURCE_DATE_EPOCH),$(shell date -u +%s))` and the epoch is
embedded in the ISO-9660 volume descriptor and FAT directory entries
(`2026111618480500` / `…0700`). Two builds of the *same* revision differ in 34 bytes.

Second finding: with `SOURCE_DATE_EPOCH` pinned — the documented, CI-used mechanism —
the build is fully deterministic. Building each revision **twice, in the same directory,
with the epoch pinned**:

```
PR#26 (170e611)  iso=793341cf100f7ed4e8ce1134a3f287161b843c8ec6164478abb788d532a9eab9
                 kernel=d61b576bfc692076e31b32750224959013e747cc4efbd71a831fb46b34f3db00
                 efi=99113ffb41bccf88892769c28df226fd006389d342fc22bb834e204063aa43e8
PR#27 (d0be617)  iso=793341cf100f7ed4e8ce1134a3f287161b843c8ec6164478abb788d532a9eab9
                 kernel=d61b576bfc692076e31b32750224959013e747cc4efbd71a831fb46b34f3db00
                 efi=99113ffb41bccf88892769c28df226fd006389d342fc22bb834e204063aa43e8
(×2 repetitions, identical)
```

So the release is isolated **by execution, not only by hash**: the three 32-bit
artefacts are bit-identical across both revisions, reproducibly. This is deliberately
more than the brief's bar ("a matching hash alone is not proof").

**Structural isolation:**

- `$(ISO)` depends only on `loader.bin`, `mbr.bin`, `kernel.bin`, `efi.img`,
  `ISO/README.TXT`, `ISO/BUILDINFO.TXT`, `tools/mkiso.py`. No path from `kernel64/` or
  `boot/uefi64/`.
- `ci/build.yml` releases come from `make release-assets` on that ISO; the `ovmf` job
  builds only `make iso` and `make uefi` (the **32-bit** UEFI loader). Nothing packages
  the 64-bit path.
- `ci/build.yml` verifies reproducibility *within* a run with pinned `SOURCE_DATE_EPOCH`
  derived from the commit — consistent with §8's first finding, and correctly implemented.
- No 64-bit marker appears in the ISO (`PC5-64BIT`, `PC5-64-LOADER`, `KERNEL64`,
  `uefi64` all absent). The one hit, `long-mode`, is the pre-existing 32-bit CPU-feature
  report string in `kernel/ui.c`, unrelated to the boot path.
- **Can 64-bit become the default shipping path?** Not without an explicit Makefile/CI
  change. It is opt-in (`make kernel64`, `make uefi64`, `make stubtest64`).

**Does the isolation test protect the intended boundary?** Yes — and it works. I
injected a violation (made release-gating `M0` depend on experimental `M5`) and it was
caught with a precise message: *"release-gating M0 depends on experimental M5"*,
5 failures. `test_the_shipped_graph_satisfies_release_isolation` walks the full
transitive closure, so an indirect dependency cannot slip through either.

## 9. Correct merge sequence for the stacked structure

`170e611` is a strict ancestor of `d0be617` and the merge base of `main..d0be617` is
`main` itself, so GitHub will show PR #27 as containing **all 25 commits** until #26 is
merged. That is the mechanical cause of a duplication risk, and it is avoidable.

**Do not merge either PR yet** — D1 and D2 are critical and are present in both heads.
Once they are fixed on a new commit (call it `F`):

1. **Fix on the top branch.** Commit the fixes for D1, D2 and D3 on top of `d0be617`

## 10. Recommendations, in priority order

1. **Do not merge.** Fix D1 and D2 first; both are in both heads, and D2 means the
   headline 64-bit evidence (`stubtest64` 22/22, `PC5-64BIT-LONG-MODE-OK`) is resting on
   a harness that does not implement the API it stands in for.
2. **Make the stub enforce the UEFI contract it models** (`AllocateMaxAddress`, and a
   fault-injection mode that returns an address above `LOAD_LIMIT`). This single change
   is what would have caught D2, and it protects every future loader change.
3. **Add a page-table walk test above 1 GiB** — the current suite provably cannot tell a
   1 GiB map from a 4 GiB one.
4. **Amend, do not erase, the "disproven" verdicts** in `TEST_RESULTS.md:2764-2765`.
   The reasoning was wrong in a specific and instructive way (PD count without PDPT
   entries); recording *that* is worth more than quietly deleting the row.
5. **Get `ovmf-test` onto a machine that has QEMU/OVMF.** D2 is exactly the class of bug
   that the first real firmware boot finds in minutes.
6. **State the `SOURCE_DATE_EPOCH` precondition** wherever the ISO hash is quoted;
   without it the build is not reproducible by 34 bytes, and a future reader comparing
   hashes across sessions will conclude something is broken when nothing is.
7. Keep PR #27's five C fixes, the brand work, the roadmap consistency and — above all —
   `PS5_SYSTEM_SOFTWARE_TARGET.md` §5. Those are careful, honest, and correct. The
   problem with this stack is not carelessness in general; it is two specific
   interfaces where the code and its stand-in drifted apart, and a test suite that was
   measuring the drift instead of the contract.
